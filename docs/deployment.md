## حالة الأتمتة: تحتاج تفعيلًا إداريًا واحدًا

كان إعداد المشروع البعيد وقت الإعداد:

```text
gitProviderOptions.createDeployments = disabled
gitProviderOptions.disableRepositoryDispatchEvents = true
```

وجود `git.deploymentEnabled: true` في `vercel.json` لا يتجاوز تعطيل Git على مستوى المشروع. موصل Vercel المستخدم لا يعرض تعديل هذا الإعداد، واتصال GitHub أعاد `403 Resource not accessible by integration` عند محاولة قراءة إعدادات الأسرار والصلاحيات. لذلك لا نعتبر النشر التلقائي مفعّلًا حتى تُنجز إحدى الطريقتين أدناه وتنجح أول عملية نشر.

### الطريقة المجهزة في المستودع: GitHub Actions

الملف `.github/workflows/ci.yml`:

1. يفحص الأنواع، PostgreSQL/RLS، هندسة الخارطة، البناء واختبارات المتصفح في كل PR.
2. يعمل بعد كل دمج/دفع إلى `main`.
3. لا ينشر إلا بعد نجاح الفحوص، وإلى معرفَي المشروع والفريق الموجودين فقط.
4. ينتظر نجاح بناء Vercel. تستخدم النسخة متغيرات Supabase الموجودة على Vercel.
5. يمكن تشغيله يدويًا على `main` من Actions.

**خطوة المسؤول الوحيدة لهذا المسار:** في GitHub افتح
`Settings → Secrets and variables → Actions → New repository secret`، ثم أضف `VERCEL_TOKEN` بقيمة رمز Vercel صالح للنشر في الفريق المستهدف. احفظه هناك مباشرة، **لا في المحادثة ولا في ملف أو commit**. يمكن استعمال سر البيئة `production` بدل سر المستودع. إن لم يوجد السر، تفشل خطوة النشر برسالة واضحة بدل نجاح صوري.

إذا كانت Actions متوقفة في المستودع، فعّلها من `Settings → Actions`. إن كانت بيئة `production` تتطلب موافقة، ستنتظر الخطوة تلك الموافقة؛ أزلها فقط إذا أردت نشرًا بلا تدخل بشري.

### بديل بلا سر Actions: تكامل Vercel مع Git

من إعدادات المشروع `voies` على Vercel فعّل Git deployments للمستودع المرتبط، وتأكد أن Production Branch هو `main` وأن GitHub App يملك الوصول إلى المستودع. يمكن إبقاء فحوص CI وإزالة/تعطيل job `production` عند اختيار التكامل الأصلي، لتجنّب نشرين لكل دمج.

لا تستخدم الطريقتين للنشر في الوقت نفسه إلا إذا كنت تريد نشرين عمدًا.

## CORS ومعاينات الفروع

دالة `journey-auth` تسمح افتراضيًا بنطاقَي الإنتاج:

```text
https://voies.vercel.app
https://voies-abdo12-dels-projects.vercel.app
```

للدخول بالرمز من معاينة فرع أو مضيف تطوير جديد، أضف **الأصل الدقيق الموثوق** إلى سر Supabase `JOURNEY_ALLOWED_ORIGINS`، مع إبقاء نطاقات الإنتاج. لا تستخدم `*` أو فتح جميع نطاقات `vercel.app`. المعاينة التي لا تملك أصلًا مسموحًا لن تستطيع استعمال دخول الرمز/إنشاء طفل، حتى لو ظهرت الخارطة.

تسجيل المدرّب بالبريد وكلمة المرور لا يحتاج إعادة توجيه OAuth. إعداد Supabase Auth يحدد موقع الإنتاج وروابطه، ويمنع التسجيل العام.

## بعد أول نشر

- راجع Deployment في Vercel وتأكد من `READY` ومن SHA الصحيح، لا من نجاح إرسال طلب النشر فقط.
- افتح موقع الإنتاج واختبر المدرّب والتلميذ على حسابين/تبويبين منفصلين.
- تحقّق من ظهور التحديث على جهاز الطفل بعد اعتماد المدرّب، ومن رفض محاولة الطفل الكتابة أو الاعتماد.
- إنشاء حساب المدرّب لا يتم تلقائيًا عند أول زيارة؛ اتبع [إعداد Supabase](supabase.md).
