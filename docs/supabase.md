# أرشيف Supabase وحسابات التصميم السابق

> **هذا توثيق تاريخي غير مطلوب للتشغيل الحالي.** بناءً على تبسيط المنصة إلى أداة تدريس صفّية، أُزيل تسجيل دخول الطالب والمعلّم وعميل Supabase من الواجهة. تُحفظ الأسماء والتقدّم محليًا، ولا تستخدم النسخة الحالية هذا المشروع أو دواله. لا تنشئ حسابات أو تعِد تطبيق الهجرة لتشغيل المنصة. احتُفظ بالملفات التالية مرجعًا فقط، ولم تُحذف الموارد السحابية أو تُعدّل في مراجعة التبسيط.

## المشروع المستقل

المشروع المخصص لهذا التطبيق هو **voies**، المرجع `wjsaqivamucqqwfzvaer`، منطقة `eu-west-1`:

```text
https://wjsaqivamucqqwfzvaer.supabase.co
```

لا تطبق هذه الملفات على المشاريع الأخرى في الحساب. نُفّذت الهجرة `journey_roles_progress_and_approvals`، وتأكدت الجداول والدوال والمنشور والصلاحيات باستعلامات لاحقة؛ سجل الخدمة أعاد الإصدار `20261111193819`.

**لا تعِد تشغيل ملف الإنشاء على المشروع الحالي**؛ أسماء الجداول موجودة بالفعل. الملف `supabase/migrations/20261111193819_journey_roles_progress_and_approvals.sql` مرجع قابل للتطبيق مرة واحدة على قاعدة جديدة، وتُضاف أي تعديلات لاحقة بهجرة مستقلة.

## نموذج الصلاحيات

- `profiles(id, role, name)`؛ إنشاء مستخدم Auth يعطي `student` دائمًا، حتى لو حملت بيانات التسجيل دورًا مزورًا.
- `students(id, name, teacher_id, login_code)`؛ ID الطفل هو ID مستخدم Auth نفسه. `login_code` هو SHA-256 للرمز، وليس الرمز المقروء.
- `progress(student_id, completed_count, updated_at, approved_by)`؛ العدد محصور في 0–32.
- RLS على الجداول الثلاثة، وسياسات `SELECT` فقط. الطفل يرى نفسه؛ المدرّب يرى الأطفال الذين يملكهم فقط.
- لا منح `INSERT/UPDATE/DELETE` للمستخدمين المسجّلين، ولا وصول مجهول للجداول. لا يستطيع المدرّب نفسه القفز إلى 32 بطلب PATCH.
- `approve_next_session(uuid)` و`undo_last_session(uuid)` دوال `SECURITY DEFINER` بمسار بحث فارغ، تفحص هوية المدرّب وملكية الطفل وتقفل صف التقدّم ثم تغيّر العدد بمقدار واحد.
- `register_student` و`consume_login_attempt` للخادم ذي `service_role` فقط. لا يمكن للطفل أو المدرّب استدعاؤهما مباشرة.
- جدول التقدّم منشور في `supabase_realtime`، مع `REPLICA IDENTITY FULL`. تبقى قراءة الأحداث خاضعة لصلاحيات القراءة.

القفل يحافظ على التغييرات المتزامنة؛ كل استدعاء RPC صحيح هو اعتماد مستقل واحد، وليس طلبًا idempotent يُعاد بلا أثر. لا تعِد طلب اعتماد فشل شبكيًا دون تحديث الحالة أولًا. الواجهة تمنع الضغط المتكرر وتراجع العدد قبل إرسال التأكيد، لكن فحص العدد في المتصفح ليس قفلًا بين جهازي مدرّب.

## إنشاء المدرّب لأول مرة

لا يوجد حساب مدرّب مفترض أو كلمة مرور افتراضية. **لم يُنشأ حساب إنتاجي بلا بريد يحدده المسؤول.** لا ترسل كلمات المرور أو مفاتيح الخدمة في المحادثة.

من لوحة Supabase الخاصة بهذا المشروع:

1. افتح `Authentication → Users → Add user` وأنشئ مستخدم المدرّب ببريد يملكه وكلمة مرور قوية، وأكّد البريد وفق سياسة البرنامج. لا تعتمد على `user_metadata.role` لإعطاء الصلاحية.
2. انسخ UUID للمستخدم الذي أنشأته، ثم من SQL Editor نفّذ الاستعلام أدناه بعد استبدال النص بين القوسين بالـUUID الفعلي. لا تستخدم ID لطفل أو لمستخدم من مشروع آخر:

```sql
update public.profiles
set role = 'teacher', name = 'اسم المدرّب'
where id = '<UUID المستخدم الفعلي من Authentication>'::uuid;
```

3. تحقق من صف واحد بالدور `teacher`، ثم سجّل الدخول من زر «المدرّب».
4. أضف طفلًا من اللوحة، واحفظ الرمز المعروض مرة واحدة وشاركه مع الطفل/وليه فقط.

الكتابة الإدارية هنا تتم من لوحة المالك الموثوقة، لا من JavaScript المتصفح. يمنع التسجيل العام (`disable_signup=true`)؛ إضافة الأطفال تتم بخادم Edge بعد التحقق من حساب المدرّب.

## دالة `journey-auth`

الشيفرة في `supabase/functions/journey-auth/index.ts`. نُشرت باسم `journey-auth`، إصدار 1، وحالتها `ACTIVE`.

- `verify_jwt=false` ضروري لأن دخول الطفل يسبق وجود JWT. لا يعني السماح بإضافة الأطفال دون صلاحية: مسار الإنشاء يتحقق من JWT عبر Auth ثم من الدور المخزن في `profiles`.
- `create-student`: ينشئ مستخدم Auth، ثم يسجل الطفل والتقدّم بصفر ذريًا. عند فشل التسجيل يحذف مستخدم Auth الذي أنشأه للتو.
- `login`: يطبع الرمز إلى عشرة رموز Base32، يبحث عن تجزئته، ويستبدل رابط Auth داخليًا بجلسة حقيقية؛ لا يُرسل رمز الخدمة إلى العميل ولا يرسل بريدًا للطفل.
- الرمز 50 بت، بصيغة `XXXXX-XXXXX`، دون 0 أو 1 أو I أو O، ويظهر مرة واحدة فقط.
- تحديد معدل دائم في PostgreSQL: 30 محاولة/دقيقة لعنوان IP، و10 للرمز، و15 لإنشاء طفل لكل مدرّب. رموز/IP المقياس مجزأة، وتنظّف النافذة القديمة عند الاستعمال.
- الردود لا تُخزّن مؤقتًا، وتُرفض الأصول غير المسموحة. GET يعيد «الطلب غير متاح»؛ هذا فحص استجابة فقط، لا اختبار كامل لتبادل جلسة الطفل.

الأسرار `SUPABASE_URL` و`SUPABASE_ANON_KEY` و`SUPABASE_SERVICE_ROLE_KEY` متاحة لدوال Supabase على الخادم. سر التطبيق `JOURNEY_ALLOWED_ORIGINS` يحتوي نطاقات الإنتاج ومعاينة الفرع المعتمدة؛ الأصول الدقيقة موضحة في `docs/deployment.md`. لا تنسخ مفتاح الخدمة إلى الواجهة.

للنشر من بيئة مسؤول لديها Supabase CLI مسجل الدخول، دون تخزين التوكن في الشيفرة:

```bash
supabase functions deploy journey-auth --project-ref wjsaqivamucqqwfzvaer --no-verify-jwt
```

## فحص حي قبل فتح البرنامج للأطفال

استخدم حساب مدرّب حقيقيًا وطفلًا تجريبيًا مملوكًا له، مع حساب مدرّب آخر عند فحص العزل:

1. سجّل المدرّب ببريد/كلمة مرور، وأنشئ طفلًا؛ يجب أن يكون العدد 0 والحصة 1 فقط متاحة.
2. من متصفح/تبويب آخر سجّل الطفل بالرمز، وافتح الحصة الأولى ثم عد؛ يجب ألا يتغيّر العدد.
3. اعتمد خطوة من المدرّب بعد التأكيد؛ يجب أن يصبح العدد 1 لدى الطرفين، مع بقاء الحصة 3 مقفلة.
4. اعكس خطوة واحدة؛ يعود العدد إلى 0. جرّب التراجع من صفر: مرفوض.
5. من جلسة الطفل، جرّب PATCH للتقدّم واستدعاء RPC الاعتماد/التراجع وقراءة طفل آخر أو تجزئة الرمز: يجب رفض الكتابات والاستدعاءات، وإخفاء الصفوف غير المملوكة.
6. جرّب مدرسًا آخر: لا يرى الطفل ولا يستطيع اعتماده.
7. اقطع اتصال الطفل ثم أعده؛ تجلب الواجهة الحالة الجديدة دون اعتماد محلي.

احذف الطفل التجريبي من Authentication بعد الفحص؛ تسلسل `ON DELETE CASCADE` يزيل ملفه وصف التقدّم. لا تحذف حساب مدرس يملك أطفالًا بلا معالجة ملكيتهم؛ مرجع `teacher_id` مقيد عمدًا.
